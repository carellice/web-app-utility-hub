# JDBC vs Hibernate — Intermediate patterns

## Hibernate Session / EntityManager

- `EntityManager` (JPA) = `Session` (Hibernate).
- Lives for a transaction's lifetime (by default in Spring).
- Holds a **Persistence Context**: a cache of managed entities (first-level
  cache).

```java
@Transactional
public void rename(long id, String newName) {
    User u = em.find(User.class, id);   // SELECT
    u.setName(newName);                  // no UPDATE here
    // at tx end: dirty check → UPDATE only if changed
}
```

## Dirty checking

Hibernate compares the current state with the initial "snapshot" and generates
the UPDATE automatically. No explicit `update()`. Handy magic, but:

- On large entities, the UPDATE includes **all** fields (you can configure
  `@DynamicUpdate` to only write the changed ones).
- DB sync happens at flush, which itself happens at tx end or before a query
  (via "auto-flush").

## Lazy loading

```java
@Entity
class User {
    @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
    List<Order> orders;
}
```

`user.getOrders()` issues the query ONLY on first access. Traps:

- **LazyInitializationException**: if the session is closed.
- **N+1 query**: a loop accessing the lazy collection → one query for the
  parent + N for the children.

N+1 fixes:

```java
@EntityGraph(attributePaths = "orders")
List<User> findAll();
```

Or JPQL `JOIN FETCH`:

```java
SELECT u FROM User u LEFT JOIN FETCH u.orders WHERE u.active = true
```

## Cascade

```java
@OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
List<Order> orders;
```

`CascadeType.PERSIST/MERGE/REMOVE/REFRESH/DETACH/ALL`. Handy, dangerous: one
save of the parent can wipe out aggregates. Use carefully, usually on clear
DDD aggregates.

## Optimistic versioning

```java
@Entity
class Order {
    @Id Long id;
    @Version Long version;
}
```

Hibernate adds `WHERE version = ?` to every UPDATE. If a concurrent update has
incremented version, the UPDATE affects 0 rows → `OptimisticLockException`.

## Batch insert

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
        order_updates: true
```

Hibernate groups INSERTs into JDBC batches. 10-50× speedup.

## Bulk update / delete

```java
@Modifying
@Query("UPDATE User u SET u.active = false WHERE u.lastLogin < :cutoff")
int deactivate(Instant cutoff);
```

Generate a single SQL. Warning: they bypass the first-level cache → clear it
(`em.clear()`) or call `flush()` first.

## JdbcTemplate: the minimal style

```java
@Repository
public class UserRepo {
    private final JdbcTemplate jdbc;
    public UserRepo(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    public User findById(long id) {
        return jdbc.queryForObject(
            "SELECT id, email FROM users WHERE id = ?",
            (rs, i) -> new User(rs.getLong(1), rs.getString(2)),
            id);
    }
}
```

In Spring 6 there is also `JdbcClient` (a more modern fluent API).

## jOOQ: typed SQL

```java
List<User> users = ctx.select(USER.ID, USER.EMAIL)
    .from(USER)
    .where(USER.ACTIVE.eq(true))
    .fetchInto(User.class);
```

Code generated from the DB. A DB refactor → compile error. Excellent for
complex queries and teams that love SQL.

## Pick layer by layer

Realistic pattern:

- **Simple CRUD** → Spring Data JPA.
- **Complex read queries** → jOOQ or JdbcTemplate.
- **Batch / ETL** → pure JDBC or Spring Batch.
- **Read model / projection** → materialized table + JdbcTemplate.
