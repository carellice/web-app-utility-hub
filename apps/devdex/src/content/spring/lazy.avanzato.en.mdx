# Advanced @Lazy — Internals, AOT, anti-patterns

## How the `@Lazy` proxy is implemented

When `@Lazy` is applied to the injection point, Spring injects not the
instance but a **proxy** generated by
`ContextAnnotationAutowireCandidateResolver`:

- JDK dynamic proxy if the target type is an interface.
- CGLIB if it is a concrete class.

The proxy keeps a reference to the `BeanFactory` and resolves the target on
the first method call. After resolution, the same target instance is reused
(singleton scope).

## Lazy + `final` field

```java
public class A {
    private final B b;
    public A(@Lazy B b) { this.b = b; }   // ok: the proxy is a concrete instance
}
```

`final` is still valid: we are storing the **proxy**, not the real instance.

## Lazy with `ObjectProvider` (cleaner alternative)

```java
public class A {
    private final ObjectProvider<B> bProvider;
    public A(ObjectProvider<B> bProvider) { this.bProvider = bProvider; }

    public void use() {
        B b = bProvider.getIfAvailable();
        if (b != null) b.do();
    }
}
```

Advantages over `@Lazy`:

- Explicit: the caller knows it is "requesting" the instance.
- No proxy, no self-invocation surprises.
- You can ask for `getIfAvailable`, `getIfUnique`, iterate with `stream()`.

## Lazy + transactional

If you inject `@Lazy MyService` where `MyService` is `@Transactional`, **the
@Lazy proxy wraps the @Transactional proxy**, and everything still works. The
JVM calls the @Lazy proxy → it instantiates the target (which is already a
@Transactional proxy) → the call goes through the tx as expected.

## Performance: what to measure

Profile with `ApplicationStartup`:

```java
app.setApplicationStartup(new FlightRecorderApplicationStartup());
```

Generates JFR `spring.beans.instantiate` events. Viewable in JDK Mission
Control.

Typical heavy culprits:

- `EntityManagerFactory` (Hibernate annotation scan).
- `DataSource` with an eagerly initialized pool.
- Reflection scanning of `@ConfigurationProperties` on large classpaths.

## AOT, GraalVM and @Lazy

In AOT/native mode:

- Lazy beans are still analyzed at build time (closed-world).
- The `@Lazy` proxy needs `RuntimeHints` for reflection on the target class.
- Spring 6 and Spring Boot 3 generate these hints automatically for standard
  patterns.

> ⚠️ Combining `@Lazy` with plugins / dynamic discovery + GraalVM is advanced
> territory. Test under `native:test`.

## Beans ALWAYS required but you want a fast startup

Pattern: **asynchronous initialization** after startup.

```java
@Component
public class Cache {
    private CompletableFuture<List<Item>> data;

    @PostConstruct
    public void init() {
        data = CompletableFuture.supplyAsync(this::loadAll);
    }

    public List<Item> snapshot() {
        return data.getNow(List.of()); // returns empty until ready
    }
}
```

The app is ready to accept requests, and the first caller either sees the
data (if already loaded) or a fallback.

## @Lazy on `@Configuration`

```java
@Configuration @Lazy
public class HeavyCfg {
    @Bean public ExpensiveBean bean() { return new ExpensiveBean(); }
}
```

All `@Bean`s inside become lazy. Equivalent to `@Lazy` on every method.

## Traps

- **`@Component @Lazy`** but then injected via an explicit eager `@Autowired`:
  the bean gets instantiated anyway, because the injection point demanded it.
- **`@Lazy` on `@Configuration`** with `proxyBeanMethods = true`: the CGLIB
  proxy is still created eagerly — laziness applies to the *produced* beans,
  not the configuration class.
- **Lazy + `BeanPostProcessor`**: PostProcessors are always eager;
  `@Lazy`-ing them has no effect.
